01整体判断

四个结构性事实决定了这个工程能不能做成，它们都是实测出来的，不是推断。

GPU 不参与颜色处理

拦截 OpenGL 实测：wglGetProcAddress 全程只被请求 1 个函数（即 OpenGL 1.1 固定管线）， 全部纹理上传都是 GL_BGRA / GL_UNSIGNED_BYTE 的 1024×1024 图块，uniform 上传数量为 0。 结论：GPU 只负责把 CPU 算完的 8-bit 成品贴上屏幕，整条影像管线都在 CPU 上——所以它可以被逐指令读出来。

参数不在二进制里，在 RAW 里

最初以为要从 Edit.exe 里挖出色彩矩阵、色调曲线、饱和度系数。 实际上引擎里对应的全是纯解包函数——从加密的 SR2SubIFD 读一段字节，按位域拆开写进参数区，不做任何计算。 相机把整套标定逐帧写进了每一张 ARW。 这条一旦确认，离线复刻就不再需要 frida：SegmentedMatrix.from_arw(path) 一行到位。

判据必须是引擎自己的成品

早期拿整幅统计量去比机内 JPEG，把上下游若干段的误差混在一起，分不清是谁的问题—— 由此得出的"缺口在 RGB2YCC"是错的（见 §07）。 真正的转折是 stage_frame.py：所有 ZcTask 共用同一套基类字段， 于是任意阶段边界上都能把整幅画面拼出来（DSC03015 是 7×5 = 35 块 1024×1024，拼出 7008×4672，与机内 JPEG 逐像素同尺寸）。 之后每一段都拿引擎自己的前后两份逐像素对，误差再也不用猜。

全自动化，无需 GUI

Edit.exe 接受命令行传图，配合 frida.spawn([EXE, arw]) 可在渲染前装好钩子、全自动完成一次完整解码，单张约 6 秒。 此前卡住整个逆向的"必须人工载图"问题由此消除，才有了后面动辄一张图跑五十次的扫参实验。

硬约束 Edit.exe 有单实例转发：上一次的进程还活着时，新 spawn 的会把文件交给它然后自己退出，钩子永远不触发。 症状是"hooks installed"之后毫无动静——与"这个阶段不执行"完全无法区分。 每次 spawn 前必须 taskkill /F /IM Edit.exe。这也是多个仪器化任务无法并行的根本原因。

02执行链

把全部 59 个 ZcTask* 的执行函数一次全钩上数出来的（stage_census.py）。 无符号表（只有 9 个导出）但保留完整 MSVC RTTI，由名字符串反查 vtable，所有 ZcTask* 的 slot 7 即执行函数。 括号里是单张图的调用次数：36 = 35 块 tile + 1 张 880×588 缩略图。

逐位/完全复刻 已解出，未接或无净效果 未复刻 不在复刻范围
  1. 01
    Preprocess×2 由 LibRaw 对位

    黑电平、白平衡等前处理。主管线走 rawpy/LibRaw（output_color=raw、gamma=(1,1)、use_camera_wb），实测与索尼喂给矩阵的像素是同一个空间：整幅对齐后逐像素相对差中位 0.20%，白平衡一致到 0.3%，最佳对角增益 ≈ 1。

  2. 02
    TileDivRough×1 无需复刻

    粗分块。分块本身不改像素值，只决定后续任务的工作单元。

  3. 03
    DemosaicRough×1 不可复刻

    去马赛克。走 GPU 加密的神经 / Vulkan 路径，不在可复刻范围内。主管线用 LibRaw 的去马赛克代替——这是残余高频误差的来源之一。

  4. 04
    ZcTaskVatr RVA 0x366920×36 仅 DRO ≠ Off 主体已解，未接入

    这就是 DRO，而它是一个双边网格（bilateral grid）局部色调映射。 gain = 2^(Tone(Mlog) − Mlog)，三通道同乘——保色是结构性的，不是巧合，正对上动态实测的三通道增益 1.030 / 1.029 / 1.028。 网格是 8×6 空间格 × 14 亮度箱，第三个轴就是像素自己的 log 亮度。

    这解开了一对看似矛盾的观测 「按输入值分箱解释掉 76% 增益方差」与「残差相关随核尺度单调上升、2052px 处还在升」—— 前者是因为双边网格的 z 轴就是像素自身亮度（同格内只有亮度相近的像素被平均进 Mlog，于是 Mlog ≈ Ylog + 小偏移）； 后者是因为粗网格只有 8×6（整幅 7008 宽 ÷ 8 ≈ 876 像素一格）。
    Auto 档位的来源
    相机算好写进 RAW 了：0x781b（10×u16 节点）+ 0x781c（28×u16 控制点），标度 1/1024，量纲 log2 亮度。引擎照搬，不是按画面现算的
    曲线形式
    28 = 9 段 × 3 + 1，分段三次 Bézier，采样成 104 项查表
    怎么定位的
    执行普查双图对照定出它就是 DRO；逐指令读 FUN_18ad50 与标定解析器定出两个 tag
    还差什么
    网格累加的三个函数、tile 坐标 → 网格坐标的 ×1/×8 映射、手动档那 10 条内置预设的 .data 表
  5. 05
    SIMDGeometricTransformCorrection×36 主管线自有实现

    几何 / 镜头校正。主管线走自己的镜头校正路径，不追求与索尼一致。

  6. 06
    SIMDLinearMatrix16 RVA 0x37e530×36 逐位 100.00%

    整条色彩链上唯一的一步，而且它不是一个全局 3×3 矩阵，是按色相分成 1024 段的一组矩阵。 逐像素索引由一个定点 atan 近似生成，是 0..1023 的色相角（整圈 1024）； 16 个标定节点环形插值成 1024 张——末段 960..1023 插回节点 0，不是钳位也不是外推。 每行和恒为 1，中性灰恒等映射。

    参数来源
    ARW → SR2SubIFD 根层 0x780f，276 字节，23×12 按 14 位定点位域拆开
    探知手段
    frida 抓参数区 + ghidra 反编译解包函数 +0x179390；src276_probe.py 抓它实际读到的入参
    还原效果
    节点系数 vs 引擎参数区最大差 0.00000000；展开的 1024 张矩阵 vs 引擎 逐位相同
    本仓库的近似
    色相索引改用真实 atan2 + 标定 LUT；高彩度处残差中位 1/1024，低彩度处无害（矩阵在那里就是恒等的）
  7. 07
    MainGamma×36 十条曲线全命中

    一张 32768 × int16 的逐通道色调 LUT，不是按图自适应的—— 它等于「创意外观的出厂曲线」叠上「机内微调」，两层都不随场景变化。 输出是 display-encoded 的（原点斜率 ~12，正是 sRGB 的 toe），横轴白点 8192，曲线饱和于索引 8084~8140， 即索尼的显示白没有高光余量。

    出厂曲线
    根层 0x74c0（uint32[10]）指向十份平行 SR2DataIFD，每份自带 128 点的 0x7805/0x7806。标度 x/128 = 索引、y/16 = 输出
    机内微调
    MakerNotes 明文 int32：Highlights 0x2033、Shadows 0x2032、Contrast 0x2004。对档位严格线性，但正负形状不同、每种外观各一套——40 条实测单位形状
    探知手段
    look_sweep.py 一张图跑五十次（十外观 × 微调档位）；换外观靠改 MakerNotes 字符串字段 0xb020
    还原效果
    让引擎轮流按十种外观渲同一张图，十条曲线全部命中，最大差 8/16384 = 0.05%
  8. 08
    RGB2YCC RVA 0x36d690×36 Y 逐位，色度差 ≤1

    饱和度与色相风格真正的产生处，而且它不是 BT.601： 色差取的是绿色差（u = R−G, v = B−G）而不是 Y 差；两个色差交叉耦合、 各自看对方的符号；最后的增益也按符号分岔。 按符号分岔的增益产生随色相变化的增益，交叉耦合产生色相旋转——正是实测到的那两样东西。 

    Y  = (R*2432 + G*4864 + B*896) >> 13
u  = R - G;   v = B - G
v2 = cross[u >= 0 ? p1 : p3] * u + v
u2 = cross[v >= 0 ? p0 : p2] * v + u
Cr = gain[u2 >= 0 ? p5 : p7] * u2
Cb = gain[v2 >= 0 ? p4 : p6] * v2
    八个参数
    0x7842 基准 + 0x7843..0x7846 四组光源增量，按 0x7848 的四个权重（和为 1024）混合
    探知手段
    反编译 FUN_14036dce0；scan_disp.py 扫全 .text 发现权重一处写入都没有——没人写却被整段读写，那就只能是从文件灌进来的
    还原效果
    Y 平面 逐位相同 100.00%，Cr / Cb 最大差 1（取整）
    顺带解释
    BW 的八个值全是 0 → 增益为零 → Cb = Cr = 0。黑白外观的去色就发生在这里，不需要任何额外机制
  9. 09
    ChromaSuppres RVA 0x36e920×36 已解，待动态定标

    两头的色度衰减，是降噪用的不是风格。 两处旧记载要改：实际是 * f >> 8 而不是 * f / 255——所以 f = 255 时色度并非完全不动，而是掉 0.39%； 并且插值出来的是「一条阈值 + 一个斜率」，不是 lo / hi 两条线。

    ISO 插值轴
    0x74a5 / 300，单位是档，锚点在 0 / −1 / −2
    六个锚点
    0x787e[0..2]（斜率族）、0x787f[0..2]（阈值族），外加 0x7880 / 0x7881。五个机型码全部取自 RAW，老机型走二进制常量
    接入前必做
    0x74a5 的物理量纲还没定死。按静态推断 ISO ≥ 400 会落到 x < −2 而两个分支都不成立——必须动态读一次 calib[0xc] 定标，不能照推断写代码
    已知影响
    用引擎自己的 YCC 走 YCC2RGB 时，中位差 2/16383、p99 118，那个残差正是还没加的 ChromaSuppres
  10. 10
    YGamma RVA 0x36f030×36 逐位 100.0000%

    只动平面 0（Y），两个色度平面改动比例 0.0000%。 pivot/contrast 这两个量就是 Fade 滑块—— pivot = 10624/16383 = 0.6485，低于它抬、高于它压，contrast < 1 时整条曲线向 0.65 收拢，正是褪色的样子。 

    y = trunc(clamp(((max(0, lut[Y]) - black) * scale - pivot) * contrast + pivot, 0, 16383))
    参数来源
    根层 0x780b（pivot）与 0x780e（contrast），各 10 项，按 Fade×10 / 10 查表线性插值
    探知手段
    slider_probe.py：改一个机内滑块，一次同时抓 tone LUT + 八个色度 short + YGamma 四标量，"这个滑块落在哪一段"通常一次就定了
    还原效果
    Fade=5 的 ARW 带公式复算，2 046 336 像素 100.0000% 逐位相同。取整是截断不是就近——就近只有 50.31% 命中
    它修的是亮度
    不是饱和度。Y 整体缩放时绝对色度不变（R−Y = 1.402·Cr），变的只是"色度/亮度"比
  11. 11
    YCC2RGB RVA 0x3713e0×36 逐位

    标准 BT.601，定点系数 14020 / 7141 / 3441 / 17720 除以 10000，输出钳在 14 位，色度以 0x8000 为中点存成 uint16。回程没有任何风格化——全部风格都在正向那一步。

  12. 12
    SIMDHueSaturation×36 仅 Saturation ≠ 0 同构复刻

    同一个因子被用了两次，方向相反。 改机内 Saturation 后 RGB2YCC 的四个增益成比例变小，而这一步乘回来（倍数 = 1 + v/100，只动两个色度平面，Y 一动不动）。 两者相消，所以这个滑块的全部可见效果，就是夹在中间的那道 ±8192 钳位：实测成品 +9 时 ×0.990、−9 时 ×1.047。

    守卫
    Imaging Edge 编辑参数 0x8016 → [rsi+0x1fc]；chain_map.py 列出全部「守卫 → 阶段」对应
    复刻做法
    与引擎同构：钳位前除、钳位后乘。诚实地说在这批照片上几乎不产生可测差别，重饱和画面上才会体现
  13. 13
    ZcTaskEffect×36 仅 Sepia 已复刻

    Sepia 的染色在这里——SE 的八个色度参数和 Standard 一模一样，所以染色一定在别处。 它把色度整个丢掉，输出只由输入的一个加权和决定，权重拟合出 (0.21, 0.71, 0.08)，不是引擎的亮度权重（用亮度权重残差翻倍）。

    怎么让它跑起来
    patch_sr2.py：索尼的 SR2 加密是 XOR 流、对合，解密 → 把根层标定整块换成第 9 份外观 → 再跑一遍 → 写回，长度和 IFD 偏移都不变
    还原效果
    三条 257 结点曲线存进 sepia.npz，三帧残差中位 11.7/16383；SE 从"回退 DCP"（色度 0.75 / 色相 +4.4°）变成 色度 1.019 / 色相 −0.28°
    一个必要的强制
    顶端夹白的结点实测会回头（最大 −70/16383），按累积最大值强制单调——染色曲线回头会在高光里翻出色斑
  14. 14
    TileDiv×35 无需复刻

    细分块。此后所有阶段都是 35 次（缩略图不再参与）。

  15. 15
    RawNRSIMD×35 形态清楚，不能照搬

    多分辨率子带阈值收缩。32768 项阈值表的生成公式已完全解出，而且它的参数全是 RAW 标签 0x78c5..0x78cb（逐图噪声模型）——这部分可以白拿。

    为什么还不能写
    正 / 逆变换核 FUN_140385af0 / FUN_1403857e0 没读，缺了它写不出可运行的复刻
    一个未验证的假定
    静态分析拿 RawNRHalf 当规范，「它与 SIMD 版同构」这条没有验证过——照搬前必须先确认
  16. 16
    SIMDITP×35 定性已知

    把三个平面拆成「基底 + 两条差分」再重建（out = base + delta），配合按置信度在滤波版与原版之间混合。 形态像是亮度降噪后重建彩色 / 抑制伪色。

    可能顺带解开 SSCS
    它是唯一重建平面数值的一步——SSCS 那个「量程只有 3043、来源未解」的悬案，源头很可能就在这里
    一条要划掉的经验
    ITP 的「标量孪生更好读」不成立：标量版与 SIMD 版共用同一批槽函数，没有省事的那条路
  17. 17
    SSCS RVA 0x3860f0×35 完全解出，但触发率 0.00%

    高光去饱和，float 与整数两条路径同构。三个通道都超过各自的 lo 时，按 G 与 min(R,B) 算出一个保留比例 k/128，把色度按比例收向灰。 实测参数 hi = 7934、lo 全是 2380，权重 [32,64,32]/128 正是亮度权重。

    量程谜团 它在 DSC03015 上一个像素都没改：35 块 tile 合计 3664 万像素，触发率 0.00%。 原因不是这张图特殊，是尺度对不上——整幅数据最大值只有 3043，而 lo = 2380、hi = 7934，数据量程只有 14 位的约 1/5。 这个量程怎么来的还没解出（试过"ITP 做 sRGB 解码"的假设，算出来应是 13874，不成立）。 别把它当成"永不执行"：真到了那个量程的图上它就会触发。
  18. 18
    AreaCompSIMD 标量孪生 0x39a0d0×35 已解，净效果 ×0.9999

    Cb-Cr 平面上的两个楔形加性修正——记忆色修正，不是全局缩放。 s 只在 Cb-Cr 平面的一个锥形区内非零；16 个 float 参数由 FUN_14039b000 按机型/模式从常量池里挑（全是 1/64 的整数倍）， 外加一个 flag 决定两个楔形是各加各的还是取交集。实测整幅色度改动 ×0.9999，所以没有接入的必要。

  19. 19
    SIMDSharpness RVA 0x388c00×35 算法已解，档位映射待定

    只动平面 0 的非锐化掩模。模糊 = 「3×3 十字核 (1,1,4,1,1)/8」与「7×7 可分离二项式 [1,6,15,20,15,6,1]/4096」按权重 t 混合； 高频过一个硬门限死区 [−hi, hi]（不是软阈值），死区外按正 / 负两条斜率放大； out = src + d·gain·taper，截断钳到 32767。

    最有价值的一条：Spica 是同一把锐化的另一端 ZcTaskSpica 用同一个强度 st[0x208] 和同一个 st[0x2c4]，但权重是 (100−r)/50—— 与 Sharpness 的 r/50 互补。两者是同一把锐化的粗端与细端， 只补 Sharpness 可能只解决一半残差。
    还差什么
    机内档位 → 编辑参数 0x801a 的换算表还没定出来。87 张素材的机内 Sharpness 全部是 +4，没有对照组
    两个会让它整个失效的分支
    st+0x2c4 只在版本 > 0x102 时才写——若残留 0 则锐化根本不生效；calib[0x1060] 在 0x78cd ≤ 256 时不被写，初值未知
    EXIF 陷阱
    Sony:0x2006 才是真值（int32s，4 字节），ExifIFD:0xa40a 恒为 Normal
  20. 20
    SIMDSpica×35 = 锐化的粗端

    边缘自适应的细锐化，与 SIMDSharpness 共用强度参数、权重互补（(100−r)/50 对 r/50）。 「语义完全未知」这条已经作废——它不是一个独立阶段，是同一把锐化拆成的两半。

  21. 21
    SIMDMarble×35 逐位复刻，但不该接

    内部色域转换：查表线性化 → 3×3（每行和为 1）→ 钳 14 位 → 查表编码。 三张 65536 项的表运行时惰性生成，静态文件里是空的，必须实机抓；拿实抓的表复算三块 tile 100.0000% 相同，最大差 0（纯解析的 sRGB / 2.2 近似不够，中位差 15、最大 260）。

    这不是输出色彩空间转换 单看这一步色度会掉两成，曾据此以为找到了缺口——但整幅一比，Marble 入口 0.9637、出口 0.9738，整段只改了 1%。 它是 Marble 自己的工作空间，末尾会转回去。把它接在我们管线后面反而更糟：色度 0.8162 → 1.1628，色相 −7.7° → −13.3°。

一次都没跑的 38 个

其中和颜色有关的：ZcTask3DLut、LinearMatrix、LinearMatrix16（非 SIMD）、ToneCurve、Effect（非 SE 时）、Dither、SIMDHueSaturation（Saturation=0 时）、ITP、AreaComp、Marble、Spica、HueSaturation。

它们照样值得反编译 每个 SIMD 任务都有一个不带 SIMD 后缀的标量孪生版，结构逐行对应但没有 AVX intrinsic 的噪声，读起来省一个数量级。 SSCS、ITP、AreaComp、HueSaturation 都是这么解出来的。 唯一确定与复刻无关的是 ZcTask3DLut：它的守卫来自 Imaging Edge 自己的编辑参数 0x8026， 跑遍十种外观、DRO 开关、全部滑块、Sepia，一次都没执行过——那是用户 LUT 功能。

03参数从哪来

这是整个工程最反直觉的结论：几乎所有渲染参数都不在 Edit.exe 里，而在每一张 ARW 自己的加密段里。 引擎那边对应的是一句 memcpy 和一个纯位域解包函数，不做任何计算。

寻址路径

IFD0 tag 0xc634 (DNGPrivateData,内联 uint32 = SR2Private IFD 偏移)
  └─ SR2Private:  0x7200 offset / 0x7201 length / 0x7221 key
  └─ XOR 流解密(同 exiftool Sony.pm 的 Decrypt,大端 uint32 异或密钥流)
       └─ SR2SubIFD 根层  ← 引擎读的是这一层
            └─ 0x74c0 = uint32[10] → 十份平行 SR2DataIFD（ST/VV/NT/PT/FL/VV2/IN/SH/BW/SE）
一个代价高昂的分歧 0x780f 在两个地方都有：根层一份，十份 DataIFD 各自还有一份。 引擎只读根层那份，逐外观的十份它根本不看——分段矩阵与创意外观无关，十种外观共用一个。 取错了会让蓝色差偏 45%、色相偏 7.6°，而且十种外观没有一种对得上。这个 bug 曾被当成"YCC 段少一步"追查了很久。

未解条目里的形态线索

145 个未命名条目并非毫无信息——项数本身就是线索。几组值得优先查的：

  • 0x7815 / 0x7816（各 SHORT×10）——紧邻 Fade 的 0x780b / 0x780e，也是 10 项。10 项 = 一个滑块的十个档位，形态上极像另一个还没定位的机内滑块的查找表。
  • 0x7820..0x782d（14 个 SSHORT×3）——连续 14 个同形条目。3 项 × 14 组，像是某个按条件选组的三系数族（与 ChromaSuppres 的 0x787e/0x787f 同为 3 项，可对照）。
  • 0x7861..0x7866（6 个 SSHORT×9）——9 项正好是一个 3×3 矩阵，六组则对应六种条件。DataIFD 里只有 0x7862..0x7866 五组，根层多一组。
  • 0x788b / 0x788c（各 SHORT×29）——29 项曲线状。0x781c 是 28 项的 Bézier 控制点，29 = 28+1 值得比对。
  • 0x797d（17）/ 0x7980（33）/ 0x7982（17）/ 0x7984（20）——17 与 33 是典型的 LUT 采样数（2ⁿ+1）。0x7980 的 33 项与 3D-LUT 的 33×33×33 网格同数，但 3D-LUT 不执行，未必相关。

05探知手段

九件工具，按"它解开了什么"排序而不是按技术栈。全部在 sony_repro/tools/。

RTTI 反查 vtable

dump_vtab.py · dump_execs.py

无符号表（只有 9 个导出）但保留完整 MSVC RTTI。由名字符串偏移 −0x10 得 TypeDescriptor，经 COL 反推 vtable。所有 ZcTask* 布局一致，slot 7 即执行函数——这一条打开了后面全部的钩子。

执行普查

stage_census.py

把全部 59 个 task 的执行函数一次全钩上，数各跑几次。定出了执行顺序，也定位了 DRO——两张只差 DRO 开关的图，普查唯一的差异就是 ZcTaskVatr 的 36 次。

整幅拼接

stage_frame.py

所有 task 共用同一套基类字段，task+0x48 是 tile 在整幅里的位置（1024 的整数倍）。于是任意阶段边界上都能拼出整幅，与机内 JPEG 逐像素同尺寸。误差定位从"拿整幅统计量猜"变成"逐像素对"。

标量孪生反编译

pyg_scalar.py（ghidra）

每个 SIMD 任务都有一个不带 SIMD 后缀的孪生版，结构逐行对应但没有 AVX intrinsic 的噪声。SSCS、ITP、AreaComp、HueSaturation 全是这么解出来的。它们不在执行路径上，正好当读物。

写入点扫描

scan_disp.py（capstone）

扫全 .text 找某个偏移的写入指令。"没人写、却被整段读写" ⇒ 只能是从文件灌进来的——光源权重就是这么从"要按色温插值猜规则"变成"直接读 tag 0x7848"的。坑：capstone 碰到解不开的字节直接停，不是跳过，必须前进一字节重扫。

抓实际入参

src276_probe.py

不去猜解包函数应该读什么，直接抓它实际读到的 276 字节。与十种外观逐字节比，分歧恰好落在字节 24..215（48 个 dword 的系数区）——五分钟定案"读错了 IFD"。先确认喂进去的是不是同一份数据，再去怀疑算法。

一次探针定位三处

slider_probe.py

改一个机内滑块，一次运行同时抓 MainGamma 的 32768 项 tone LUT、RGB2YCC 的八个色度 short、YGamma 的四个标量。"这个滑块落在哪一段"通常一次就定了，不必先拼整幅再逐段比。

重写加密段

patch_sr2.py

SR2 的 XOR 加密是对合的，跑两遍回到原文。解密 → 换掉根层标定 → 再跑一遍 → 写回，长度与 IFD 偏移都不变。这是真正切换外观的唯一办法，Sepia 的 ZcTaskEffect 就是这么逼出来的。

批量扫参

look_sweep.py

命令行传图 + frida.spawn，单张约 6 秒，一张图跑五十次覆盖十种外观 × 全部微调档位。所有"对档位是否线性""正负形状是否相同"的结论都来自这里。

与 DCP 路径的对照

与正确匹配的 DCP profile 相比互有胜负，sony 路径的 RMSE 普遍更好，色相误差在低饱和场景下本身就不可靠。 （原先"2~9° vs 9~15°"的压倒性对照不成立——那是拿 ST profile 去比 FL/VV2 的图，把 DCP 一方压低了一倍有余。）

顺带解答了一个悬念：索尼没有单独的 camera→标准空间转换矩阵。 16 个节点矩阵全部贴着单位阵（对角 0.96~1.03，非对角 ±0.17），整条色彩链就这一个近单位的分段微调—— 也就是说 ILCE-7CM2 的原生基色本就接近 Rec.709，Adobe 绕道 XYZ 反而引入了误差。

07剩下的缺口

静态反编译一轮之后，缺口的性质变了：从「不知道它在做什么」变成「知道公式，缺一两个标定量或一个未读的核」。

  1. 锐化的档位映射 算法已解

    非锐化掩模的核、死区、双斜率全部解出，但机内档位 → 编辑参数 0x801a 的换算表还没定。障碍依旧是没有对照组：87 张素材的 Sony:0x2006 全部是 +4。

    首选路线是 frida 在渲染前直接改内存里的锐度参数——同一张图上扫参数，画面完全受控。而且现在知道必须连 Spica 一起扫：两者共用强度、权重互补，只标定一半会得到系统性偏低的锐化量。

  2. DRO 的网格几何 主体已解

    双边网格的形状、色调曲线的来源与求值方式都清楚了，而且 Auto 不再是障碍——曲线是相机算好写进 RAW 的。

    剩下的是三个网格累加函数、tile 坐标 → 网格坐标的 ×1/×8 映射（预览图与全幅的对齐关系，得动态量一次），以及手动档那 10 条内置预设的 .data 表。

  3. RawNR 的变换核 缺一块

    阈值表的生成公式与它的全部输入（RAW 标签 0x78c5..0x78cb）都拿到了，但正 / 逆变换核没读，所以现在写不出可运行的复刻。

    另有一个未验证的假定：静态分析拿 RawNRHalf 当规范，而「它与 SIMD 版同构」这条从没验证过。照搬之前必须先确认，否则会重演「读了不在执行路径上的那个类」那类错误。

  4. ITP 与 SSCS 的量程 同一个谜

    ITP 的形态（基底 + 两条差分重建）已知，但数值语义未定。它很可能同时是 SSCS 那个量程悬案的答案——SSCS 阈值 lo=2380/hi=7934 而实测数据最大值只有 3043，触发率 0.00%，而 ITP 是链上唯一重建平面数值的一步。

  5. ChromaSuppres 的插值轴定标 差一次动态读数

    六个锚点与插值公式都齐了，只差 0x74a5 的物理量纲。按静态推断，ISO ≥ 400 会落到 x < −2、而两个分支都不成立——这说明推断有误。必须动态读一次 calib[0xc] 定标，不能照推断写代码。

  6. 去马赛克 不可复刻

    GPU 加密的神经 / Vulkan 路径，不在范围内。主管线用 LibRaw 代替，这部分残差是结构性的，不会归零。

08被推翻的结论

这一节和上一节同样重要。以下每一条都曾经写进笔记、指导过若干天的工作，然后被实测推翻。

  • DRO 的 Auto 档位由引擎按画面自行决定，相机只写下 Auto 决定的是相机，结果以 Bézier 曲线写进 RAW（0x781b / 0x781c）。离线复刻不需要重建判级逻辑 —— 已离线核对：两个 tag 确实存在、项数正好 10 与 28、除以 1024 后值域正好落在 [0, 13]，与 vatr[0x70] = log2(8191) 吻合
  • SIMDSpica 语义完全未知，是一个独立阶段 它与 SIMDSharpness 共用强度参数、权重互补，是同一把锐化的粗端与细端
  • ChromaSuppres 中间调 f=255 时完全不动 实际是 * f >> 8 而非 /255，f=255 时色度掉 0.39%；且插值出来的是「一条阈值 + 一个斜率」而非 lo/hi 两条
  • ITP 的标量孪生版更好读 标量版与 SIMD 版共用同一批槽函数，这条对 ITP 不成立（对 SSCS / AreaComp / HueSaturation 仍然成立）
  • PIPELINE §4 的 lv 与各任务里的「标定块」是两块内存 是同一块（ChromaSuppres 两条路都用、且同由 FUN_14015f540 写）。所以 +0xf82、+0xdec、+0xae、+0x10f2 这些偏移全在一块里
  • 0x7805 与 0x7806 是并列的一对 128 点外观曲线 十份 DataIFD 里 0x7805 完全相同、只有 0x7806 有 7 种取值 —— 只有后者是外观的定义
  • tone LUT 是按图自适应的 是「外观出厂曲线 + 机内微调」，两层都不随场景变化。误判来自只比了两张外观不同的图
  • 节点表 = f(创意外观, 白平衡)，规则未解 它不是任何东西的函数，是相机逐帧写进 RAW 的标定数据。所有怪象（45/56 张表相同、取值不随白平衡单调、连拍相邻帧跳表）一次全解释
  • ZcTaskVatr 不在执行链上 那份普查跑的全是 DRO=Off 的图。它就是 DRO
  • DRO 对应 ZcTaskAreaComp AreaComp 从未执行；跑的是 AreaCompSIMD，而且只在 Cb-Cr 平面做楔形加性修正，整幅色度 ×0.9999
  • DRO 没有空间成分（相关系数 ≈ 0） 第一版用 33×33 核，实际只覆盖 132 个原始像素。相关随核尺度单调上升，2052px 处已到 −0.34
  • 缺口在 RGB2YCC，色度还差两成 YCC 段逐像素正确（Y 逐位相同，色度差 ≤1）。真正的误差在上游：矩阵读错了 IFD
  • BW / SE 的色彩矩阵是单位阵 那是逐外观的 0x780f，引擎压根不读它。十种外观共用同一个矩阵，去色全在 YCC 段
  • Marble 的色域转换就是那个缺失的两成色度 整段净效果只有 1%（入口 0.9637 → 出口 0.9738）。那是它自己的工作空间，末尾会转回去；强行接上反而更糟
  • SSCS 处理的帧与画面无关（相关系数 ≈ 0） 那是拿整幅去比一块 tile。把那块 dump 出来渲成图，是画面一角的局部放大，内容完全对得上
  • 系统性偏饱和 5%，来自某个未复刻的后段阶段 是 Highlights / Shadows 整条读不到。补上之后色度 0.9263 → 0.9983、色相 −0.69° → −0.01°
  • YGamma 的 pivot=0 / contrast=1.0547 是常数 因为手上 65 张全是 Fade=0。一个"测出来是常数"的量，先确认样本里那个开关有没有被拨动过
  • sony 路径的色相精度压倒性优于 DCP（2~9° vs 9~15°） 对照组拿的是 ST profile 而图是 FL/VV2。公平重测后互有胜负，sony 的 RMSE 普遍更好

09会骗人的手法

这些不是"结论错了"，是实验手法本身会给出看似合理的假读数。每一条都值得在动手前先读一遍。

改 MakerNotes 换外观，只换得动曲线 引擎的 0x14036dce0 一看到 calib+0x1c != 0 就直接抄根层那份"相机已混合好的"八个 short（0x7841）， 根本不看你选了哪个外观。所以 look=BW 渲出来的图不是黑白的，look=SE 和 look=BW 输出完全一样。 用这种补丁看曲线的数据仍然有效，看颜色的结论一律不成立。要真的换外观，必须改加密段里的根层标定。
exiftool 的同名标签 Sony MakerNotes 和 ExifIFD 带同名标签：Sony:0x2006 Sharpness = +4（真值）vs ExifIFD:0xa40a Sharpness = Normal； Sony:0xb025 vs Sony:0xb04f 的 DynamicRangeOptimizer 同理。 exiftool -j 只返回一个，而且返回哪个没有保证。必须用 -a -G1:2 -H -s 列全。 我曾据此差点把新语料判成"锐度对照组"。
靠指针配对前后两份 想法是：若两个阶段共用缓冲区，同一个 data 指针上就能拿到"曲线前"与"ITP 后"两份。指针确实重合了 6 个，但内容完全对不上（前后中位数之比在 0.09 到 228 之间，毫无规律）。 原因是缓冲区被内存池回收后复用——指针相同只说明这块内存被用过两次。要配对必须拿 tile 的矩形，不能靠地址。
竖幅的图 stage_frame.py 的画布写死是横的 7008×4672，而 rawpy 会按 EXIF 方向出片。 转错方向比不转还糟——会把色相差算成 30°。现在按相关性自动选 rot90。
研究工具与产品实现脱节 e2e_pipeline.py 有一份自己的 sony_chroma，给主管线加 YGamma 时忘了同步它， 于是这套工具量出来的亮度整体偏 +0.021，看着像"复刻偏暗"，其实只是工具没跟上。

两个接入时的结构性决定

曲线所在的基色是 profile 的属性，不是用户的外观选择。 MainGamma 是逐通道曲线、作用在 camera/Rec.709-ish 空间，而前端的 u_profile_lut 也是逐通道但作用在 ProPhoto——同一条曲线在不同基色下逐通道应用结果并不相同。 解法是给视图变换加一个 u_profileCurveSrgb 开关，跟着 colorProfile.kind 走，协议零改动。

下发的 y 必须先解 sRGB 编码。 索尼的 LUT 输出是 display-encoded 的，而前端视图变换的契约是输出 display-linear，最后统一做一次 sRGB 编码。不解就会 gamma 两次。

此外不再烘焙任何曲线常量。"按外观烘焙曲线"那个设计本身就是错的——烘焙进去的所谓"FL 曲线"其实混进了那批照片的机内 Highlights −6，被当成了外观的定义。

十种外观现在全部可渲染，而且可以自由切换

UNRENDERABLE_LOOKS 已清空。BW 靠 0x7842 全零自然去色，SE 靠已复刻的 ZcTaskEffect 染色曲线，都不再回落 DCP。

切换外观不需要重新解码 分段矩阵是机身的，存在 SR2SubIFD 根层、十种外观共用一份， 所以换外观改变的只有色调曲线和色度项——两者都在下发给浏览器的那 75 kB profile 里。 实测确认而非推断：十种外观走同一个 276 字节 param_block，线性输出逐位相同（最大差 0）。 于是外观选择器与那五个微调滑块走同一条 /look-profile 通道，几十兆的画面留在 GPU 上不动。

外观清单从文件本身读（每份 DataIFD 的 0x7770 经与 exif 同一张表归一成代码）， 不是硬编码的十个位置。所以一台写了 FL2 / FL3 的机身，它的 ARW 会自动在选择器里多出这两项—— 客户端不需要先认识它们，认不出的代码就按原样显示。
