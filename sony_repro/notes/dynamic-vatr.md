# `ZcTaskVatr`(DRO)—— 参数块与「Auto 定档」的位置已找到,传递函数尚未闭合

RVA `0x366920`。**第 0 步已验证**:新语料 `E:\temp_photo` 上 `ZcTaskVatr` 确实执行
36 次,排在 `DemosaicRough` 之后、`SIMDGeometricTransformCorrection` 之前,
与 PIPELINE §3 记的完全一致。

## 1. 最重要的一条:**PIPELINE §7.10 的增益数字不具代表性**

§7.10 的「×1.048@128 → ×1.020@1024」是在 DSC02961 / DSC02962 上量的 —— 那是
旧语料里仅有的两张 DRO 图。把 22 张新 DRO 图的强度都读出来之后可以确认:
**这两张恰好是整批里 DRO 最弱的**(强度 0.091 / 0.029 stop,见 §3 的表)。

拿强度最高的 DSC02948(0.727 stop)重跑 `vatr_probe.py`:

| 输入 | 128 | 256 | 512 | 1024 | 2048 | 8192 |
|---|---|---|---|---|---|---|
| DSC02948 增益 | **×1.632** | ×1.544 | ×1.394 | ×1.090 | ×0.926 | ×0.9995 |
| DSC02867 增益 | ×0.977 | ×0.988 | ×0.994 | ×0.997 | ×0.999 | ×0.9996 |

DSC02867 的 EXIF 同样写着 `DynamicRangeOptimizer = Auto`,**但引擎自动判定的档位
是 0,整段等于不做**。22 张新图里有 3 张是这样(DSC02867 / DSC02868 / DSC02954)。

> **所以「DRO=Auto」不等于「有 DRO」。** 按 exif 一律套一条固定的 DRO 曲线,
> 在这 3 张上会直接做错;在 DSC02948 这种图上则会严重欠量(要 ×1.63 而不是 ×1.05)。
> 而且 DSC02948 是**又抬暗部又压中调**(2048 处 ×0.926),不是单纯提亮。

## 2. 参数块在哪

反汇编 `0x140366920` 开头:

```
P = *(task + 0x68) + 0xC01C0            ← 注意:不是 lv = *(*(task+0x68)+0xc8)
                                          是同一个对象里另一段,而且没有再解引用
P[0x48] / P[0x4c] / P[0x50]   三个 float,被 shufps 广播(疑似三通道)
P[0x74]                       float;当 *(param3+8)[0x238] == 1 时改用常量 1.0
                              (0x238 就是 §7.8.5 的 VatrFloat 守卫 = 编辑参数 0x8023)
P[0x960] / P[0x964] / P[0x968]
P[0xd8]                       int,后面拿来算 (n-2) / (n-1)
```

**实测 16 张图 `[opts+0x238]` 恒为 1**,所以 `P[0x74]` 那条路从不走,强度不是它。

### 块内已认出的东西(`tools/vatr_param.py` + `vatr_diff.py`)

| 偏移 | 内容 |
|---|---|
| `+0x6c` / `+0x84` / `+0xc4` | 同一个整数,逐图变(263~739),疑似某个统计量的量化结果 |
| `+0x8c` | float,8.07~11.73,**log2 单位**(疑似高光锚点) |
| `+0x90` | float,4.09~6.90,log2 单位(疑似阴影锚点) |
| `+0x98` / `+0x9c` / `+0xa0` | (计数, Σx, Σx²) 三元组,x 是 log2 单位 |
| `+0xa8` / `+0xac` / `+0xb0` | 第二组 (计数, Σx, Σx²) |
| **`+0x7c8` .. `+0x960`** | **103 个 float —— 这就是 DRO 曲线**,x = (i+1)/8(log2),y 也是 log2 |
| `+0x96c` 起 | `log2(8k)` 静态查表(0, 3, 4, 4.585, 5, 5.3219, …),用来把像素值转 log2 |

曲线两端都是恒等(i=0 时 0.1249 ≈ 0.125,i=102 时 12.8746 ≈ 12.875),中段抬起。

## 3. **「Auto 档位」只有一个自由度**

把 16 张图的曲线减去恒等,得到「增量曲线」(单位 stop),做 PCA:

```
奇异值(相对第一个): 1.000  0.102  0.035  0.028  0.0035 …
前 1 / 2 / 3 个主成分解释的方差: 98.77% / 99.80% / 99.92%
```

**第一主成分就解释 98.8%** —— 也就是说曲线形状基本固定,逐图只差一个**强度标量**。
离线复刻「自动判级」于是从「重建整套判级逻辑」降级成「估出一个数」。

各图强度(增量曲线的峰值,单位 stop;峰值位置几乎恒在 log2 ≈ 6.1~6.5,即输入 70~90):

| 图 | 强度 | 图 | 强度 | 图 | 强度 |
|---|---|---|---|---|---|
| DSC02948 | **0.727** | DSC02857 | 0.260 | DSC02953 | 0.095 |
| DSC02858 | 0.590 | DSC02951 | 0.214 | DSC02961 | **0.091** |
| DSC06800 | 0.427 | DSC09758 | 0.134 | DSC02962 | **0.029** |
| DSC02865 | 0.426 | DSC02859 | 0.128 | DSC02867 | **0.000** |
| | | DSC02861 | 0.125 | DSC02868 | **0.000** |
| | | DSC02947 | 0.032 | DSC02954 | **0.000** |

(粗体三张 = 完全不做;DSC02961/62 = §7.10 当年量的那两张。)

### 强度由什么决定:**是相机决定的,曲线原样写在 ARW 里**(已验证,16/16)

> 我先在块内找了一圈:每个 dword 对强度求相关**最高只有 |r| = 0.44**,
> 用 `(1, P[0x8c], P[0x90])` 回归整条曲线只解释 **3.9%** —— 于是一度写下
> 「强度是引擎按画面现算的,建议下写断点抓写入方」。**这是错的。**
> `notes/static-vatr-dro.md` §5 从反编译给出答案:曲线来自 SR2 标签
> **`0x781b`(10 个 uint16 节点)/ `0x781c`(28 个 uint16 控制点)**,
> 是**分段三次 Bézier**,引擎只是照着生成 104 项查找表,不做任何判级。

拿我已经抓下来的 16 份参数块做离线核对(`tools/vatr_verify.py`,**不用开 Edit.exe**):

```
knot[i] = tag0x781b[i] / 1024        ctrl[i] = tag0x781c[i] / 1024
step = vatr[0x70] / 104              curve[i] = min(Bezier3(ctrl[3j..3j+3], u), vatr[0x70])
```

| 图 | flag | vatr[0x70] | 与引擎 `vatr+0x7c4` 的最大差 | RMS |
|---|---|---|---|---|
| 全部 16 张 | 1 | 12.99982 | **≤ 0.000003** | ≤ 0.000001 |

**逐图命中,误差只有 float32 的噪声。「Auto 档位没人记下来」这道坎不存在** ——
相机把判级**结果**以曲线形式写进了 RAW,离线解 `0x781b`/`0x781c` 即可,
不需要重建任何自动判级逻辑。

顺带把静态那边 §8 点名要核对的量都对了一遍(实测 16 张全一致):

| 量 | 静态预期 | 实测 |
|---|---|---|
| `vatr+0x48/4c/50` 亮度权重 | 0.1495 / 0.2935 / 0.0570 | ✅ 一致 |
| `vatr+0x70` log 域上限 | ≈ 12.9998 | ✅ 12.99982 |
| `vatr+0x74` 细节保留 C | 1.0 | ✅ 1.0 |
| `vatr+0x964 / +0x968` 正负强度 | 都 1.0 | ✅ 都 1.0 |
| `vatr+0xd8` 亮度分箱数 | 14 | ✅ 14(且 `+0xdc` = 12.9998/14 = 0.92856) |
| `[opts+0x238]`(Auto 守卫) | == 1 → C = 1.0 | ✅ 16/16 都是 1 |

> 我原先把曲线记成「+0x7c8 起 103 项」——**差了一项**,起点是 `+0x7c4`、共 **104** 项。
> 我的 x 轴 `(i+1)/8` 其实就是静态的 `i * vatr[0x70]/104`(从 i=1 数起),两者等价。

## 4. 传递函数:量清楚了,但**和块里那条曲线对不上**

### 4.1 方法:往输入平面灌均匀场(`tools/vatr_flat.py`)

Vatr 的曲线是渲染开始前按整幅统计算好的,所以在某块 tile 的 `onEnter` 里改输入
**不会改变曲线**,正好把「同一条曲线下输出如何依赖输入」隔离出来。

`--const V` 把**所有 tile** 灌成同一个值,一次运行同时得到 35 个不同空间位置上的响应。

DSC02857(强度 0.260),取各 tile 的众数增益:

| 输入 | 16 | 32 | 64 | 128 | 256 | 512 | 1024 | 2048 | 4096 | 8192 |
|---|---|---|---|---|---|---|---|---|---|---|
| 增益 | 1.125 | 1.1875 | 1.1875 | 1.1875 | 1.1953 | 1.1953 | ~1.15 | ~1.07 | ~0.988 | 0.9998 |
| stop | 0.170 | 0.248 | 0.248 | 0.248 | 0.257 | 0.257 | ~0.20 | ~0.09 | −0.017 | −0.000 |

块里那条曲线在同样的 log2 位置上给出的是:

| 输入 | 16 | 32 | 64 | 128 | 256 | 512 | 1024 | 2048 | 4096 |
|---|---|---|---|---|---|---|---|---|---|
| stop | 0.176 | 0.228 | **0.259** | 0.196 | 0.110 | 0.033 | −0.019 | −0.005 | −0.000 |

**峰值高度一致(0.257 vs 0.259),但实测的平台宽得多** —— 曲线在 log2=6 处见顶就掉,
实测从 32 一直平到 512。任何单一的 x 轴缩放都对不上(要求的比例在 4 到 13 之间飘)。

**这不是矛盾,是曲线的自变量不是像素值。** 静态那边给出的式子是

```
y    = 0.1495R + 0.2935G + 0.0570B          (读平面时先 >>1)
Ylog = log2(2y)
Mlog = 双边网格在 (x, y, Ylog) 上三线性插值出来的**局部对数亮度均值**
gain = 2^( Tone(Mlog) − Mlog )              (C = 1 时)
```

曲线吃的是 `Mlog` 而不是 `Ylog`。**平台之所以比曲线宽,正是因为 `Mlog` 被局部均值
拉住、不跟着 `Ylog` 一比一走。** 我实测的传递函数因此是「曲线 ∘ 网格」的复合,
不该期望它等于曲线本身 —— 之前把这条写成「对不上、待解」是我判断错了。

### 4.2 空间项**不来自这块 tile 自己的内容**

把整块 tile 灌成完全均匀的 1024,输出行内仍然有 1142..1166 的起伏(±1%);
灌 256 时不同 tile 的增益从 1.1396 到 1.1953 不等。**输入完全均匀而输出不均匀**,
只能说明空间项来自**渲染前算好的一张(低分辨率)图**,不是当场从 tile 内容算的。

这和 §7.10「残差与邻域均值的相关随核尺度单调上升,2052px 处仍在升」是同一件事的
两面 —— 那个「核」大到超出单块 tile,本来就不可能是 tile 内的卷积。

**静态那边给出了原因**:双边网格是从**预览图**建的(`FUN_1401887b0` 先取
`arw->vt[0x110]()` 的预览),空间格只有 **8 × 6**,整幅 7008 宽 ÷ 8 ≈ 876 像素一格。
我这个「输入完全均匀而输出仍有 ±1% 起伏」的观测,就是网格来自预览而非当前 tile
内容的**独立实证**。

> ⚠️ **一个会骗人的做法(我踩了):** 先用 120px 的均匀色块做色阶去量曲线,
> 得到一条「从 32 到 768 都是 1.1875」的平台曲线。那是错的 —— 色块比空间核小得多,
> 块内的「邻域」根本不是块自己的值。
> 换成「每块 tile 一个值」也仍然有偏:35 块 tile 的空间上下文各不相同,
> 输入值和空间项被混在一起。**只有 `--const`(所有 tile 同一个值、逐值多次运行)
> 才把两者分开。**

### 4.3 顺带量到的

* 输出有硬上限:DSC02857 上输入 ≥15360 一律输出 **15020**。
* 输入 ≤ 16 时(在部分 tile 上)增益恰为 1.000,存在一个下端不作为的区间。
* 三通道输出完全相同(注入的是中性灰),即增益是保色的,与 §7.10 一致。

## 5. 还差什么(给下一棒的人)

曲线和整条逐像素公式都已闭合,**只剩双边网格的建法**:

1. **网格累加**(`FUN_140188b60` / `0x189220` / `0x1895a0`)—— 8×6 空间格 × 14 亮度箱,
   每格累 (num, den),静态那边没逐行读。
2. **渲染时 tile 坐标 → 网格坐标的映射**(静态 §4 的 `S = 1.0 或 8.0`)。
3. 这两条都适合用注入法量:`vatr_flat.py --const V` 已经能给出
   「同一输入在 35 个空间位置上的增益」,反解 `Mlog(x, y, Ylog)` 是可行的;
   再抓一次 `vatr+0xc0` 指向的 8×6 块数组(每块 0x40 字节)就有真值对照。

**不要按 exif 的 `Auto` 套一条固定曲线** —— 见 §1,同为 `Auto`,
不同照片的曲线从「完全不动」到「+0.73 stop」都有,而这条曲线**逐图现读 RAW 就有**。
